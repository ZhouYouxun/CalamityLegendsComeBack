# 如何避免 AI 味道过重

> 本文讨论的目标，是让共享源码仓库、提交差异、PR 和发布包保持“零非产品残留”：不出现个人 AI 工具目录、提示词、会话记录、临时脚本、反编译器缓存、教程式废稿和与项目风格冲突的生成式代码。
>
> 这不是一份伪造“完全由人工手写”身份、篡改历史或欺骗审查者的指南。AI 可以参与开发，但最终提交必须真正经过开发者理解、取舍、重写、测试和负责。若项目要求披露 AI 使用情况，应按项目规则如实处理。

## 一、先把目标说准确

“不能出现一丝一毫的 AI 痕迹”在这里应当被解释为以下可验证标准：

1. 项目工作树内不存在 `.codex-tools`、个人提示词、对话导出、AI 临时报告、自动生成草稿和个人工具二进制。
2. Git 跟踪列表、提交差异、PR 和最终打包文件中不存在上述内容。
3. 正式源码没有教程式口吻、Markdown 加粗符号、emoji 步骤编号、大段失效实现和逐行复述代码的注释。
4. 新代码服从目标项目原有的命名、文件组织、绘制管线、UI 架构、联网约定和注释密度。
5. 每一行提交内容都能由贡献者解释、修改和维护；不能解释的部分不提交。
6. 外来代码、贴图、音频和 Shader 都有可核实来源，不能通过删注释或改变量名冒充原创。

这个标准能够保证共享仓库干净，但不能保证拥有本机访问权限的人无法发现外部个人工作目录。外部仓库是交付隔离方案，不是本机取证隐身方案。

## 二、当前 CLCB 仓库已经确认的事实

### 1. `.codex-tools` 实际是什么

CLCB 中的 `.codex-tools` 不是模组源码，而是一套 ILSpy 反编译命令行工具及其 .NET 工具缓存：

- 共 67 个被 Git 跟踪的文件。
- 体积约 19.5 MB。
- 没有正式 C# 源码依赖这个目录。
- `.gitignore` 和 `.tmodignore` 当前已经包含 `.codex-tools` 排除项。
- `V1.0` 已通过提交 `5eae384c` 解除跟踪。
- 当前 `DEV` 仍然跟踪旧文件，因为忽略规则不会自动取消已经进入 Git 的文件。

因此，不需要继续改写两个忽略文件。它们当前的规则已经足够。真正的问题只是旧文件仍在 `DEV` 的 Git 索引中。

### 2. 外部仓库不能修复已经存在的历史

把以后所有 Codex 资料放到外部，可以阻止再次污染项目；但它不能让已经提交过的 `.codex-tools` 无痕消失。

对当前 `DEV` 只有三种事实上的状态：

- 保持跟踪：GitHub 和克隆仓库中继续存在这些工具文件。
- 做一次正常清理提交：解除跟踪，旧历史仍然保留。
- 重写仓库历史：影响所有协作者和分支，不应仅为了隐藏工具痕迹而进行。

推荐第二种。在干净分支中执行：

```powershell
git rm -r --cached -- .codex-tools
git commit -m "Stop tracking local ILSpy tool cache"
```

`--cached` 只解除 Git 跟踪；由于现有忽略规则仍在，本地工具可以继续保留。这个提交是可解释的仓库卫生工作，不需要伪装成其他功能提交。

如果是在一个全新的项目中，则不要复制 `.codex-tools`，也不要先创建再忽略。工具从第一天开始就应位于项目外。

## 三、推荐的外部管理仓库

建议建立一个完全独立于任何 ModSources 项目的个人仓库：

```text
C:\Users\wangk\Documents\CodexLocalWorkspace\
├─ .git\
├─ README.md
├─ projects\
│  ├─ CalamityLegendsComeBack\
│  │  ├─ PROJECT.md
│  │  ├─ STYLE_PROFILE.md
│  │  ├─ REVIEW_CHECKLIST.md
│  │  ├─ PROVENANCE_WORKING.md
│  │  ├─ prompts\
│  │  ├─ scratch\
│  │  └─ audits\
│  └─ 新项目代号\
│     ├─ PROJECT.md
│     ├─ STYLE_PROFILE.md
│     ├─ REVIEW_CHECKLIST.md
│     ├─ PROVENANCE_WORKING.md
│     ├─ prompts\
│     ├─ scratch\
│     └─ audits\
├─ tools\
│  └─ ilspy\
└─ outputs\
```

这个仓库可以只存在本机；如果需要跨设备同步，必须使用私有仓库，并且不得写入账号令牌、Cookie、私钥、未公开项目源码和第三方保密材料。

不要使用以下连接方式把它重新暴露给项目：

- 不要把外部仓库做成项目的 Git 子模块。
- 不要在项目中创建指向外部目录的 junction 或符号链接。
- 不要在项目根目录保留一个“入口文件”指向个人 AI 工作区。
- 不要把提示词、会话日志或个人审计结果作为项目资源打包。

Codex 仍然可以直接读取和修改真正的源码目录；外部仓库只负责个人上下文、草稿、工具和审查记录。源代码与个人辅助资料不需要位于同一仓库。

## 四、外部仓库中每个文件应该写什么

### 1. `README.md`

只写外部仓库的职责和边界：

```markdown
# Codex Local Workspace

本仓库仅保存个人开发辅助资料、项目风格摘要、提示词、临时审计结果和本地工具。

规则：

1. 不保存账号令牌、Cookie、私钥和密码。
2. 不复制无权再分发的第三方源码、贴图和音频。
3. 不把本仓库链接、嵌套或打包到任何正式项目中。
4. 所有准备提交的代码必须回到目标项目中单独审查、编译和测试。
5. 外部审计记录不能替代目标项目要求的许可证和署名文件。
```

### 2. `projects\项目代号\PROJECT.md`

记录项目位置和工作边界，不保存项目源码副本：

```markdown
# 项目入口

- 源码目录：C:\完整路径\ModSources\项目目录
- 默认分支：由实际项目决定
- 构建方式：记录项目真实使用的构建命令
- 允许修改范围：仅限当前任务明确点名的目录
- 禁止写入源码仓库：prompts、scratch、audits、tools、会话导出、反编译输出
- 代码权威：目标项目当前源码、许可证和维护者决定
```

如果项目路径发生变化，只改外部 `PROJECT.md`，不要在源码仓库中增加 Codex 专用配置文件。

### 3. `STYLE_PROFILE.md`

这是最重要的文件。它不应该写抽象的“写优质代码”，而应记录从目标项目真实源码总结出的具体约定：

```markdown
# 项目代码风格摘要

## 参考文件

- 参考文件 A：项目维护者近期编写的同类 Projectile
- 参考文件 B：项目当前使用的 UI 或绘制系统
- 参考文件 C：项目当前 Shader 注册与卸载方式

## 命名与组织

- 命名空间格式：待从项目核实
- 类名、字段名、私有字段前缀：待从项目核实
- 一个文件允许包含的主要类型数量：待从项目核实
- partial、region、嵌套类的使用习惯：待从项目核实

## 绘制约定

- SpriteBatch 的 Begin/End 由谁负责
- 世界坐标与屏幕坐标的转换位置
- AlphaBlend、Additive、Immediate 的恢复方式
- Dedicated Server 下的资源加载保护
- Trail、Primitive、RenderTarget 和 Screen Filter 的项目标准入口

## 联机约定

- Projectile 由 owner、服务器还是所有客户端生成
- ai/localAI/SendExtraAI 的使用边界
- 纯视觉效果是否允许仅在本地生成

## 注释风格

- 只解释意图、约束、坐标空间、性能原因和异常状态
- 不复述下一行代码
- 不使用 Markdown 加粗、emoji 步骤号和教程式章节
- 不在正式文件保留废弃实现
```

每加入一个新项目，都应重新生成这份风格摘要。不能把 CLCB 的风格模板直接套给另一个团队。

### 4. `REVIEW_CHECKLIST.md`

建议写成每次提交前都能逐项勾选的清单：

```markdown
# 提交前审查

- [ ] 本次差异只包含任务要求的文件
- [ ] 没有个人工具、提示词、会话、截图缓存和临时报告
- [ ] 没有注释掉的旧版本或调试代码
- [ ] 没有 `// **...**`、emoji 编号和逐行教学注释
- [ ] 新类型和新抽象在项目中确有必要
- [ ] 所有常量均有玩法、视觉或性能依据
- [ ] 每一行新增代码都能人工解释
- [ ] SpriteBatch、RenderTarget、Shader 和资源状态均正确恢复
- [ ] 多人模式中的生成所有权已经核实
- [ ] 专用服务器不会加载客户端图形资源
- [ ] 外来代码和资源已经完成来源核实
- [ ] 已运行格式检查、编译和必要的实机测试
- [ ] PR 说明写清设计原因、测试方式和已知限制
```

### 5. `PROVENANCE_WORKING.md`

这是个人工作阶段的来源台账：

```markdown
# 来源工作台账

| 内容 | 来源 | 权利状态 | 最终处理 |
|---|---|---|---|
| 数学公式 | 公开数学概念 | 公式概念不作为个人专有资产 | 自行实现并说明游戏化设计 |
| 线段绘制 | 目标项目现有基础 API | 依项目许可证 | 使用项目标准接口 |
| Shader A | 本人从零实现 | 待核实目标项目贡献规则 | 可提交 |
| Shader B | 从第三方代码修改 | 需要检查许可证和署名 | 未确认前禁止提交 |
| 贴图 C | 第三方项目资源 | 专有或来源不明 | 禁止复制 |
```

注意：如果最终代码确实包含需要署名或附带许可证的内容，正式项目内仍必须存在相应的 `LICENSE`、`THIRD_PARTY_NOTICES` 或项目规定的署名。不能因为个人台账位于外部，就把法律要求也藏在外部。

### 6. `prompts\`、`scratch\`、`audits\`

- `prompts\`：只保存个人提示词模板。
- `scratch\`：保存废弃实现、实验公式、反编译片段和临时转换结果。
- `audits\`：保存本地差异审查、性能记录和未准备公开的分析。

这些内容不得复制进项目。真正有价值的设计结论应由开发者重新组织成符合项目语气的设计说明，而不是直接提交对话文本。

## 五、不改项目忽略文件的本地保护

最根本的规则仍然是：个人工具从一开始就不要在项目目录中生成。

为了防止误操作，可以增加一个用户级 Git 排除文件。它不修改任何项目的 `.gitignore` 或 `.tmodignore`。

建议文件：

```text
C:\Users\wangk\.config\git\ignore
```

建议只加入明确属于个人的临时名称：

```gitignore
.codex-tools/
.codex-scratch/
*.codex.tmp
```

然后在本机配置：

```powershell
git config --global core.excludesFile "C:/Users/wangk/.config/git/ignore"
```

这项配置只应作为误写保护，不能代替外部目录原则。

不要在全局排除文件中宽泛加入以下名称：

```gitignore
.codex/
AGENTS.md
CONTRIBUTING.md
```

这些文件在某些团队中可能是正式项目配置或贡献规范。全局忽略它们可能导致开发者看不到本应提交的团队文件。正确方法是不要在源码目录创建个人 `.codex` 内容，而不是把所有同名文件一律隐藏。

## 六、正式项目中允许和不允许出现什么

### 可以出现

- 真实参与构建和运行的源码。
- 项目自己拥有或有权分发的贴图、音频和 Shader。
- 团队共同采用的构建脚本、格式规则和贡献规范。
- 法律要求的许可证、版权和第三方署名。
- 解释复杂算法、坐标约束、性能决策和同步规则的必要注释。
- 团队明确要求保存的设计文档和测试材料。

### 不应出现

- `.codex-tools`、个人 `.codex` 工作目录和 AI 会话导出。
- `prompt.md`、`chat.txt`、`conversation.json` 等个人对话材料。
- 反编译器、反编译输出、NuGet 工具缓存和临时 DLL。
- 为一次任务生成的审计脚本、批处理草稿和一次性截图缓存。
- “下面我们实现”“确保 Shader 存在”“第一步/第二步”之类教程口吻。
- `// **应用 Shader**`、`1️⃣` 等 Markdown 或聊天式装饰。
- 大段注释掉的第一版、第二版、失败版代码。
- 为显得像人工而故意加入的错别字、无意义缩写和不一致格式。
- 通过改名、换色、删署名包装成原创的第三方内容。

## 七、当前代码中最需要优先清理的“重味道”问题

### 1. Shader 文件不应兼任实验笔记

当前 `CyberNeonGlow.fx`、`GlitchBlocksShader.fx`、`BlackHoleDistortion.fx`、`TrailWarpDistortion.fx` 等文件带有不同程度的教程式注释、失败版本和 C# 使用示例。

正式 `.fx` 文件建议只保留：

1. uniform、sampler 和矩阵定义。
2. 必要的输入输出结构。
3. 实际使用的辅助函数。
4. Vertex/Pixel Shader。
5. technique/pass。
6. 少量解释坐标、采样、兼容性或性能原因的注释。

失败版本应进入外部仓库的 `scratch\shaders\`，Git 历史本身也已经能够保存正式文件的旧版本。正式项目不需要再次存放整段废稿。

### 2. 过大的单文件应按职责拆分

当前项目存在约 95 KB 的 ParticleLab 文件、约 118 KB 的 Matrix Attacks 文件和约 90 KB 的 Matrix New Modules 文件。文件很大并不自动意味着 AI，但巨型 switch、大量重复样板和多个系统混在同一文件中，会让审查者难以判断设计责任，也会放大任何不自然风格。

带到新项目时应拆成：

```text
EffectWorkbench\
├─ EffectCatalog.cs
├─ EffectDefinition.cs
├─ EffectPreviewHost.cs
├─ EffectWorkbenchState.cs
├─ EffectWorkbenchView.cs
└─ Adapters\
   ├─ ParticlePreviewAdapter.cs
   ├─ PreDrawPreviewAdapter.cs
   └─ ShaderPreviewAdapter.cs
```

HDMC 几何系统则建议拆成：

```text
ProjectedGeometry\
├─ GeometryDefinition.cs
├─ GeometryProjection.cs
├─ GeometryEdgeBuilder.cs
├─ ProjectedGeometryRenderer.cs
└─ Effects\
   ├─ HypercubeField.cs
   ├─ LorenzField.cs
   └─ CliffordField.cs
```

拆分目的不是制造“人工感”，而是建立清晰的所有权、依赖和测试边界。

### 3. 通用 Shader 不等于个人代表作

彩虹、灰度、扫描线、像素化、简单正弦 UV 扭曲等都是常见技术。它们可以作为工具，但不能仅凭本地存在一个 `.fx` 文件就当作核心原创能力。

真正适合成为代表作的是：

- 参数能够影响明确空间结构，而不只是换色。
- 效果与攻击阶段、角色状态或目标位置绑定。
- Shader 与 C# 调用端形成完整接口。
- 具有真实武器消费者并经过实机调参。
- 不依赖无法再分发的第三方资源。

当前适合继续提炼的方向包括 SHPC 激光染色拖尾、局部漩涡和引力透镜。`HGTShader.fx` 与灾厄文件完全一致，`ArtAttackTrail.fx` 的有效正文来自灾厄；这两项不能作为个人原创礼物。

## 八、怎样让 AI 辅助代码真正成为可负责的项目代码

### 第一步：先写设计，不先生成实现

在外部 `PROJECT.md` 或任务草稿中先写清楚：

- 玩家看到什么。
- 效果在什么状态出现。
- 哪一层拥有计时和状态。
- 哪一层只负责绘制。
- 多人模式由谁生成。
- 依赖哪些项目现有接口。
- 明确不能复制哪些第三方内容。

只有这些问题已有答案后，才让 AI 协助编写局部实现。

### 第二步：每次给出项目原生参考

每个任务只选择最接近的两三个目标项目文件作为风格权威。要求实现服从这些文件，而不是服从某个通用“高级 C# 风格”。

重点对齐：

- 命名空间与目录。
- private 字段、属性和常量命名。
- 大括号、空行和 target-typed `new` 使用习惯。
- 资源加载和卸载。
- SpriteBatch 状态管理。
- Projectile owner 与网络同步。
- 注释语言和密度。

### 第三步：限制差异规模

一个提交只解决一个功能。不要把以下内容混在一起：

- 新特效。
- 无关格式化。
- 文件改名。
- 公共工具重构。
- 旧系统清理。
- 数值平衡。

差异越聚焦，贡献者越容易逐行负责，审查者也越容易确认设计是否合理。

### 第四步：进行人工改写与删除

人工审查不是简单阅读一遍，而是主动执行：

- 删除无法解释的保护性判断。
- 删除没有真实第二个消费者的抽象层。
- 合并只做一次转发的 Helper。
- 把常量改成符合玩法与画面的真实参数。
- 将通用变量名改成项目领域名称。
- 删除重复注释和废弃代码。
- 核实 API 是否是目标项目当前真实用法。
- 逐项测试专用服务器、多人模式和资源卸载。

如果贡献者无法脱离 AI 修复这段代码，就还不应该提交。

### 第五步：用证据代替“像不像人工”的争论

一次成熟的 PR 应能给出：

- 为什么需要这个功能。
- 为什么选择当前架构。
- 哪些数学概念是公共知识。
- 哪些视觉节奏和游戏化组合是本次原创设计。
- 使用了哪些现有项目接口。
- 有无第三方内容及其许可证。
- 编译结果、实机截图或视频。
- 多人模式和性能测试结果。
- 已知限制和后续工作。

这类证据比故意制造“不完美的人类代码”可靠得多。

## 九、提交前的静态仓库检查

以下检查用于发现非产品残留和意外文件，不应机械删除合法项目内容。

### 1. 检查工作树

```powershell
git status --short
git diff --check
```

逐个确认所有新文件。不能因为文件处于未跟踪状态就默认安全。

### 2. 检查可疑工具与草稿名称

```powershell
git ls-files | rg -i "codex|openai|chatgpt|prompt|conversation|scratch|ilspy|decomp"
```

出现结果后人工判断。合法的游戏文本或团队正式文件不能仅因名称命中就删除。

### 3. 检查教程式和聊天式注释

```powershell
rg -n "//\s*\*\*|1️⃣|2️⃣|3️⃣|下面我们|确保.*存在|应用 Shader|恢复.*绘制" -g "*.cs" -g "*.fx"
```

命中不等于有罪，但正式源码中的教程结构、emoji 和 Markdown 装饰通常应重写为简短的工程注释。

### 4. 确认本地工具没有被跟踪

```powershell
git ls-files ".codex-tools/**"
```

正确结果应为空。对其他个人目录也应进行同类检查。

### 5. 检查最终差异

```powershell
git diff --stat
git diff
```

审查重点：

- 是否修改了任务之外的文件。
- 是否意外重排整个文件。
- 是否出现新的无意义抽象。
- 是否把实验记录放入正式源码。
- 是否混入个人路径、用户名和本机工具路径。
- 是否丢失许可证、署名和来源说明。

## 十、三项原创能力应怎样带到新项目

### 技术价值顺序

1. HDMC 投影几何与状态化战斗系统。
2. 已有真实消费者的参数化 Shader。
3. 调试与预览工作台。

### 实际合并顺序

1. 先提交一个适配对方 UI 的 `EffectWorkbench` 骨架，不包含灾厄粒子条目。
2. 再为对方现有的一次攻击接入一个局部漩涡、引力透镜或参数化拖尾。
3. 建立信任后，再提交一个轻量的投影几何演示，只包含一个几何体、一个状态和一个用途。

这样既能展示能力，也不会在刚加入时强行把整套 CLCB 视觉身份压到别人项目中。

HDMC 带过去时应保留的是：

- 顶点和边的数据表达。
- 旋转平面与投影算法。
- 投影结果和攻击位置之间的连接。
- 状态、时间与几何反馈之间的关系。

应当替换的是：

- 灾厄 Line、Bloom、Ring、Star 等资源路径。
- 灾厄粒子类和 Shader 注册。
- CLCB 声音与专有命名。
- 当前整件武器的数值、模块调度和视觉配色。

最基础的线段可以直接使用 `MagicPixel` 拉伸绘制，因此几何核心不需要携带任何灾厄贴图。

## 十一、许可证与来源边界

CLCB 当前根目录的 `LICENSE` 是 MIT；CalamityMod 的 `LICENSE.md` 则把源码、视觉、音频、名称和品牌列为专有内容。

因此必须分别处理：

- CLCB 自有 MIT 代码可以在保留许可证要求的前提下复用。
- CLCB 中引用灾厄 API，不等于取得灾厄资源的再分发权。
- 灾厄贴图、声音、Shader 正文和直接复制的 C# 代码不能因为位于 CLCB 中就自动变成 MIT。
- 数学公式属于公开知识范畴，但具体实现若来自第三方源码，仍需按来源许可证处理。
- 如果新项目要求贡献者转让版权或授予独占许可，应先确认自己确实拥有相应权利。

外部 `PROVENANCE_WORKING.md` 用来防止开发阶段混淆；正式许可证和第三方声明必须按照新项目规则进入正式仓库，不能为了“零 AI 痕迹”一并删除。

## 十二、最终原则

最严格、也最可靠的做法不是研究怎样伪装，而是建立以下工作纪律：

1. AI 工具和个人资料永远位于项目外。
2. 项目忽略文件只服务团队共同需要，不为个人工具反复留下修改记录。
3. 所有提交从目标项目现有风格出发。
4. 正式源码不保存实验过程，只保存最终必要实现。
5. 每行代码都经过人工理解、删改、测试和承担责任。
6. 第三方来源与许可证不能隐藏。
7. 不伪造手工痕迹，不篡改历史，不对维护者撒谎。

按照这套方法，静态审查者在共享项目中看到的只会是项目需要的源码、资产、测试和许可证，而不会看到个人 AI 工作环境留下的目录、缓存、提示词和草稿。这才是可以长期维持的“零非产品残留”。
