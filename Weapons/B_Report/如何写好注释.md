# 如何写好注释

## 写在前面

注释不是给编译器看的，也不是拿来证明自己懂多少术语的。说白了，它就是你给后来维护代码的人留的一句话。这个“后来的人”很可能还是几个月后的自己，所以注释最好别写得像论文、接口手册或者教学文章，而应该像两个熟人吃饭时聊项目：话不用端着，但事情得说清楚。

这份办法的核心只有一句：

> 用平时说话的方式，把代码里看不出来的那部分讲明白。

代码已经写出来的东西不用再翻译一遍。真正值得留下的是：这里该改什么、什么别动、为什么这么写、动错了会怎样，以及当初踩过什么坑。

## 一、我们想要的到底是什么语气

推荐的语气是“熟悉项目的人顺手提醒一下”，不是“老师开始讲课”，也不是“为了显得像真人故意乱说”。

例如：

```csharp
// 伤害都在这里调，列顺序别改：阶段、突击、复苏、侦查、轰炸、瘟疫。
// 阶段索引依赖下面这个顺序，蜂后固定排在骷髅王前：
// 开局 -> 克眼 -> 邪恶 Boss -> 蜂后 -> 骷髅王 -> 困难模式……
```

这段话自然，不是因为用了中文，也不是因为用了“别改”，而是因为它真的在帮人干活：

- 第一行告诉你去哪改，以及哪些东西绑在一起。
- 第二行告诉你这里有固定索引，不能随便重新排序。
- 第三行直接把正确顺序摆出来，省得以后的人再猜。

如果写成下面这样，意思虽然没错，但书面味会重很多：

```csharp
// 此处用于配置各个阶段对应的伤害数值。
// 需要注意的是，阶段索引依赖于下述顺序，因此不得随意调整各元素的位置。
// 阶段顺序依次为：开局、克苏鲁之眼、邪恶 Boss、蜂王、骷髅王以及困难模式。
```

问题主要出在“此处用于”“需要注意的是”“因此不得”“依次为”这些表达。它们不是错，只是像在写说明书。日常维护代码时，完全可以说得更直接：

```csharp
// 各阶段伤害在这里调。顺序别动，后面的索引直接拿它。
// 蜂后排在骷髅王前：开局 -> 克眼 -> 邪恶 Boss -> 蜂后 -> 骷髅王 -> 困难模式……
```

## 二、口语化不等于随便写

口语化的重点是“自然、直接”，不是故意写错字，也不是每句话都塞进语气词。

下面这些词通常很好用：

- 这里
- 这边
- 其实
- 先
- 再
- 就
- 别
- 别顺手
- 故意
- 不然
- 说白了
- 真要改的话
- 稍微
- 先留着
- 后面还要用
- 这块只管……

例如：

```csharp
// 这里其实不用重新找目标，上一段已经把索引同步过来了。
```

```csharp
// 先把旧的 RenderTarget 还回去，后面还要重新申请，别一直占着。
```

```csharp
// 这边只管画，伤害和碰撞都在 Projectile 里算，别顺手塞进来。
```

```csharp
// 真要改范围的话调上面的半径就行，下面几个比例都是跟着它走的。
```

这些句子听起来像平时说话，但信息仍然很准。

下面这些词要少用：

- 此处
- 该对象
- 上述内容
- 需要注意的是
- 值得一提的是
- 基于上述原因
- 从而
- 进而
- 以实现……效果
- 对其进行处理
- 确保……能够正常执行
- 综上所述

它们不是禁词，不过一小段注释里接连出现，马上就会变成论文或技术文档口吻。

例如：

```csharp
// 对粒子的速度向量进行旋转处理，从而实现围绕中心进行运动的视觉效果。
```

可以直接改成：

```csharp
// 速度往切线方向偏一点，火花看起来就会绕着中心转。
```

再比如：

```csharp
// 需要注意的是，该逻辑仅应由弹幕所有者执行，以避免在多人模式中产生重复实体。
```

可以改成：

```csharp
// 只让 owner 生成，不然几个人联机就会多出好几份。
```

后者既短，也更像真正处理过这个问题的人留下的话。

## 三、写注释前先想六件事

不要一看到代码就马上开始翻译。先问自己六个问题：

```text
入口：以后想改这个效果，应该从哪下手？
对象：这段真正控制的是什么？
约束：什么东西不能随便动？
原因：为什么要这样写？
后果：如果改错了，具体会坏在哪里？
例子：有没有固定顺序、范围、例外或特殊情况？
```

不一定每段注释都要回答六个问题。一般挑代码本身看不出来的两三个写就够了。

还是拿阶段表举例：

```text
入口：伤害在这个表里调。
对象：每一列对应一种模块。
约束：列和阶段的顺序都不能乱。
原因：后面通过固定索引取值。
后果：顺序一乱，数值就会套到别的阶段或模块上。
例子：蜂后固定排在骷髅王前。
```

把这些事实压成两三行，就是：

```csharp
// 伤害都在这张表里调，列顺序是：阶段、突击、复苏、侦查、轰炸、瘟疫。
// 后面直接按索引取值，所以顺序别动；蜂后固定排在骷髅王前。
```

这就是生成自然注释最稳定的办法：先拿到事实，再把事实说成人话。

## 四、六种最常用的注释

### 1. 告诉别人去哪改

这类注释主要是给以后调数值、换颜色、改速度的人指路。

推荐写法：

```csharp
// 左键的速度和转向都在这里调。
```

```csharp
// 五种模块的颜色统一从这里取，外面别再单独写一套。
```

```csharp
// Shader 参数都集中在这段，Projectile 里只负责把状态传进来。
```

```csharp
// 想改拖尾长度就动这个缓存，下面的宽度不用跟着改。
```

不推荐把它写成一段介绍：

```csharp
// 本方法主要负责对左键攻击的速度以及转向相关参数进行统一配置。
```

平时没人这么说话。直接说“都在这里调”就够了。

### 2. 告诉别人什么别动

只说“不要修改”不太够，最好把原因或者后果顺手带上。

```csharp
// 数组长度别改，模块编号就是直接拿它当索引用的。
```

```csharp
// 这里别换成 Main.myPlayer，联机时真正生成弹幕的是 owner。
```

```csharp
// 这个 `Begin` 和后面的 `End` 是一对，中间再开一次 SpriteBatch 会直接炸状态。
```

```csharp
// 最后两帧先留着，拖尾还要靠它们收干净。
```

这种语气听起来不正式，但比“严禁修改”更有用，因为它告诉你为什么。

### 3. 解释为什么故意这样写

代码里最该注释的，往往是那些看上去“不太对”，其实是特意留下来的地方。

```csharp
// 这里故意慢一拍，先让预警圈亮出来，玩家才来得及看懂攻击方向。
```

```csharp
// 蜂后固定放在骷髅王前，阶段存档最开始就是按这个顺序记的。
```

```csharp
// 没直接 Kill，最后这点时间是留给淡出和收尾音效的。
```

```csharp
// 这里故意不用完全随机，节点间距太乱的话矩阵轮廓就看不出来了。
```

“这里故意……”是很好用的开头，不过别每段都用。也可以换成：

```csharp
// 先别急着删，这两格空位是给后面的特殊阶段留的。
```

```csharp
// 看着像多算了一次，其实这里拿的是更新后的目标位置。
```

```csharp
// 多留这一层不是为了更亮，它负责把边缘从背景里托出来。
```

### 4. 记录踩过的坑

这类注释最有“项目自己的味道”，因为它来自真实问题，不是从语法书里抄来的。

```csharp
// oldPos 前几格有可能还是 Vector2.Zero，连线前先跳过，不然会从屏幕左上角扯一条线过来。
```

```csharp
// 别让所有客户端都生成，四个人联机就会变成四份伤害。
```

```csharp
// 半径不能给零，Shader 中间会直接冒出一块黑的。
```

```csharp
// 这里如果先恢复 AlphaBlend，后面的光圈就会整个暗下去。
```

```csharp
// 面板关掉就行，别把玩家上次选的页码也一起清了。
```

注意，没真正确认过的问题不要装成踩坑经验。可以写：

```csharp
// 这里可能会遇到重复生成，联机还没测，先别把 owner 判断删掉。
```

但正式合并前最好把问题测清楚，再改成确定的说法。

### 5. 解释数学和视觉目的

不要逐行翻译公式。读代码的人看得懂 `Sin`、`Lerp` 和向量旋转，真正难猜的是你想让画面变成什么样。

不推荐：

```csharp
// 使用正弦函数计算半径变化。
// 将方向向量旋转九十度得到切线方向。
// 生成一个随机速度。
```

推荐：

```csharp
// 半径稍微上下摆一点，别让整个圆环转得像焊死了一样。
```

```csharp
// 速度以切向为主，再往中心收一点，火花会从核心旁边掠过去。
```

```csharp
// 随机量只打散角度，不碰基础间距，不然矩阵的轮廓会被冲散。
```

```csharp
// 每个节点错开一点相位，转起来就不会全挤在同一边。
```

```csharp
// 近处压得更狠一点，才会有往黑洞里陷进去的感觉。
```

这里可以多用“稍微、看起来、别让、不然、才会”这类日常表达。它们很适合描述视觉目标，比“通过某某公式实现动态效果”清楚得多。

### 6. 划清职责边界

一段代码只管什么、不管什么，最好说清楚。这样以后的人不容易顺手把逻辑越堆越乱。

```csharp
// 这边只管画，伤害和碰撞还是 Projectile 自己算。
```

```csharp
// 这里只挑目标，不生成弹幕；真正开火在模块计时器那边。
```

```csharp
// 面板只改本地选择，真要同步的时候走 packet，别在 Draw 里发。
```

```csharp
// 这个类只保存几何数据，颜色和线宽交给外面的 renderer。
```

常用结构是：

```text
这里/这边只管……，……还在另一边处理。
这个类只记……，别把……也塞进来。
这里只改……，真正的……走原来的系统。
```

## 五、语气词怎么用才自然

语气词确实能让注释没那么书面，但不能每句话都来一遍。一个注释块里有一两个就够了。

### “其实”

适合纠正表面理解：

```csharp
// 这里其实不是伤害判定，只是拿同一条线画预警。
```

```csharp
// 看着像随机乱转，其实每个节点都有固定相位。
```

### “先”与“再”

适合说明顺序真的很重要：

```csharp
// 先把旧状态还原，再开 Additive，顺序反了会把后面的 UI 一起染亮。
```

```csharp
// 先锁目标，再把位置写进 ai[]，客户端拿到的是同一份结果。
```

### “就”

适合告诉别人修改入口很简单：

```csharp
// 想改范围就调这个半径，下面几个比例会自己跟着走。
```

```csharp
// 没目标就按原方向飞，别在这里突然停下来。
```

### “别”与“不然”

适合写真实后果：

```csharp
// 别在 Draw 里改 AI，不然帧率一变，行为也会跟着变。
```

```csharp
// 这张纹理要用 PointClamp，不然像素边缘会糊成一圈。
```

### “说白了”

适合把复杂概念压成一句，但不要频繁使用：

```csharp
// 说白了，这个值就是“模块还有多久能再开一次”。
```

```csharp
// 说白了，这层只负责把黑色背景挖掉，不参与真正的扭曲。
```

### “顺手”

适合提醒别人别越界改东西：

```csharp
// 这里只关面板，别顺手把玩家当前选择也清掉。
```

```csharp
// 调颜色的时候别顺手改透明度，Additive 下两者看着像一回事，实际不是。
```

### 少用“啊、呀、啦、嘛、呗”

这些词在聊天里自然，放进长期维护的源码里容易显得过头：

```csharp
// 这里就不要乱改啦，不然会出问题呀。
```

这句话既没说哪里会坏，也像在刻意表演口语。改成下面这样更好：

```csharp
// 顺序别乱，模块编号直接拿它当索引，错一位后面就全串了。
```

## 六、把书面语改成平时说话的办法

### 1. “用于”改成“管的是”或直接说动作

```csharp
// 该字段用于存储当前目标的索引。
```

改成：

```csharp
// 这里记的是当前目标索引，没目标时就是 -1。
```

### 2. “进行”通常可以直接删掉

```csharp
// 对目标位置进行插值处理。
```

改成：

```csharp
// 位置慢慢追过去，别一帧直接贴到目标身上。
```

### 3. “确保”改成真实后果

```csharp
// 确保 SpriteBatch 状态能够得到正确恢复。
```

改成：

```csharp
// 画完切回 AlphaBlend，后面的原版东西还要接着画。
```

### 4. “避免”改成“不然会怎样”

```csharp
// 避免多人模式下重复生成弹幕。
```

改成：

```csharp
// 只让 owner 生成，不然每个客户端都会来一份。
```

### 5. “实现某种效果”改成画面到底怎样

```csharp
// 通过正弦函数实现动态起伏效果。
```

改成：

```csharp
// 半径来回晃一点，圆环看着不会那么死。
```

### 6. “需要注意的是”直接删掉

```csharp
// 需要注意的是，该值不得小于零。
```

改成：

```csharp
// 别给负数，后面拿它算数组位置。
```

如果没有具体后果，就写：

```csharp
// 最小是零。
```

短一点反而更好。

## 七、同一件事的三种写法

### 例子一：多人模式

书面写法：

```csharp
// 为了避免在多人模式下生成重复的弹幕实例，该逻辑仅由弹幕所有者执行。
```

教程写法：

```csharp
// 首先判断当前玩家是否为弹幕的所有者。如果不是，则不执行弹幕生成逻辑。
```

推荐写法：

```csharp
// 只让 owner 生成，不然每个客户端都会多打一轮。
```

### 例子二：绘制状态

书面写法：

```csharp
// 在完成加法混合绘制后，需要恢复默认混合状态，以防止影响后续绘制流程。
```

教程写法：

```csharp
// 结束当前 SpriteBatch，随后使用 AlphaBlend 重新开始 SpriteBatch。
```

推荐写法：

```csharp
// 光效画完切回 AlphaBlend，后面的 UI 还要接着用。
```

### 例子三：数学随机化

书面写法：

```csharp
// 在基础角度的基础上添加随机偏移，以提升粒子分布的自然程度。
```

教程写法：

```csharp
// 调用 NextFloat 方法生成一个随机数，并将其加到当前角度上。
```

推荐写法：

```csharp
// 角度稍微打散一点就行，基础间距别动，不然圆环会散架。
```

### 例子四：状态顺序

书面写法：

```csharp
// 状态枚举值的排列顺序与数组索引存在对应关系，因此请勿调整。
```

教程写法：

```csharp
// 数组会根据状态枚举的整数值访问对应的元素。
```

推荐写法：

```csharp
// 状态编号就是数组下标，顺序一动，后面的数据就全对不上了。
```

### 例子五：延迟销毁

书面写法：

```csharp
// 为保证视觉效果能够完整播放，此处不立即销毁弹幕。
```

教程写法：

```csharp
// 将弹幕的 timeLeft 设置为两帧，使其在两帧后被销毁。
```

推荐写法：

```csharp
// 先别立刻 Kill，最后两帧要把拖尾和声音收完。
```

## 八、哪些注释干脆不要写

### 1. 复述下一行代码

```csharp
// 将透明度设置为零。
Projectile.Opacity = 0f;
```

删掉就行。代码已经说得很清楚。

### 2. 解释常见语法

```csharp
// 遍历所有 NPC。
foreach (NPC npc in Main.ActiveNPCs)
```

也可以直接删掉。除非这次遍历只挑某种特殊 NPC，应该注释的是筛选原因。

### 3. 没有依据的情绪

```csharp
// 我也不知道为什么，反正别改。
```

这种话看着口语，实际上没有维护价值。真不知道时，可以老实标出尚未核实：

```csharp
// 这里去掉后会让第二阶段提前结束，具体是哪条同步路径还没查清，先留着。
```

它同样很自然，但至少把已知现象和未知部分分开了。

### 4. 为了显得像真人故意加废话

```csharp
// 这个嘛，其实大概就是这么回事，应该不用管。
```

这不是口语化，是信息不足。注释可以轻松，但不能含糊。

### 5. 已经过期的历史

```csharp
// 第一版写坏了，第二版也不行，这是第三版。
```

旧实现交给 Git 历史或外部实验记录。正式源码只说明当前版本为什么这样做。

## 九、专业词汇该不该保留

避免过量专业词汇，不等于把所有项目术语都翻译成日常中文。

下面这些词在 tModLoader 项目里本来就是正常交流的一部分，可以直接保留：

- owner
- ai[] / localAI[]
- oldPos
- Projectile
- NPC
- SpriteBatch
- RenderTarget
- Shader
- PreDraw
- Additive / AlphaBlend
- dedicated server
- packet
- hitbox

强行翻译反而不自然：

```csharp
// 仅由抛射物的所有权持有者在本地生成该实体。
```

不如直接写：

```csharp
// 只让 owner 生成，不然联机会重复。
```

真正需要减少的是为了显得专业而加上的空壳词汇，例如“生命周期管理机制”“视觉表现层级”“参数化动态演算过程”。如果一句普通话能说清楚，就用普通话。

例如：

```csharp
// 该变量负责控制视觉表现层级中的生命周期衰减过程。
```

可以改成：

```csharp
// 这个值管淡出，归零以后就不再画了。
```

## 十、注释长度怎么控制

### 一行就够

简单约束、修改入口和短警告尽量一行说完：

```csharp
// 只改颜色，透明度交给外面的淡出。
```

### 两到三行最常用

先说结论，再补原因或顺序：

```csharp
// 伤害都在这里调，列顺序别改。
// 后面的模块直接按索引拿值，错一列就会整排串掉。
```

### 长注释只留给真正复杂的规则

如果涉及存档兼容、网络所有权、矩阵投影或特殊状态机，可以写长一点，但仍然要像人在解释问题，而不是写论文摘要。

```csharp
// 这四个值不是普通的二维坐标，它们先在 XW、YZ 两个平面里转，
// 再把 W 压进 XYZ，最后才投到屏幕上。顺序别换，换了以后虽然还能画，
// 但内外两层会黏在一起，超立方体基本就看不出来了。
```

这段用了专业概念，但语气仍然自然，因为每句话都在解释实际画面。

## 十一、怎样稳定生成这种注释

如果需要让 Codex 或其他辅助工具生成这种风格，不要只说“帮我加中文注释”。应该提供四样东西：

```text
1. 这段代码平时主要改什么。
2. 哪些东西不能动。
3. 当初为什么这样写。
4. 改错后会出现什么具体问题。
```

然后给出明确语气要求：

```text
注释使用自然中文口语，像同事吃饭时聊代码。
少用“此处、该对象、需要注意的是、从而、进而、进行、确保”等书面表达。
可以用“这里、其实、先、就、别、故意、不然、顺手、稍微”等日常说法。
保留 owner、ai[]、SpriteBatch、Shader 等项目术语，不强行翻译。
只解释代码看不出来的原因、约束、后果和踩坑，不逐行复述语法。
不知道的原因不要编造，也不要写“反正如此”。
每段通常控制在一到三行。
```

生成之后还要人工检查三个问题：

1. 这句话真的是自己平时会说的吗？
2. 它有没有补充代码本身看不出来的信息？
3. 半年后的人看见它，能不能少踩一个坑？

三个答案都是“是”，这条注释基本就能留下。

## 十二、可以直接使用的句式库

这些句式只是帮忙起头，不能每段机械套用。

### 修改入口

```text
……都在这里调。
想改……就动这个，下面会自己跟着走。
……统一从这里取，外面别再写一份。

```

顺序别动，后面直接拿它当索引。

## 十三、提交前检查

写完注释后，逐条看一遍：

- 有没有在复述下一行代码？有就删。
- 有没有“首先、接下来、最后”这种教程结构？有就改。
- 有没有“此处、该对象、进行、确保、从而”连着出现？有就说得直接一点。
- 有没有解释真正的原因、约束或后果？没有就想想这条注释还需不需要。
- 有没有为了显得口语而加无意义废话？有就删。
- 有没有装作知道一个其实没确认的原因？有就明确写成待核实。
- 有没有把 owner、Shader、SpriteBatch 之类正常术语硬翻成别扭中文？有就换回来。
- 同一个注释块里语气词是不是太多？留一两个就够。
- 这句话读出来像不像自己平时会对同事说的话？不像就再改一次。
- 如果删掉这条注释，后来的人会不会少知道一件重要的事？不会的话，可以不留。

## 十四、最后定下来的规则

以后写中文注释，优先遵守下面这些规则：

1. 用平时说话的方式写，别端着。
2. 少用书面语、学术词和为了显得专业而加的空壳表达。
3. 可以用“这里、其实、先、就、别、故意、不然、顺手、稍微”等自然语气。
4. 一段话里语气词别堆太多，口语化不是表演。
5. 先说结论，再补原因；能一行讲完就别写三行。
6. 重点写修改入口、固定约束、真实原因、具体后果、踩坑和职责边界。
7. 不逐行解释语法，不写教程，不给代码做中文翻译。
8. 专业名词该留就留，别把 owner、ai[]、Shader、SpriteBatch 强行翻译。
9. 不知道原因就别编，可以把已知现象和还没查清的部分分开写。
10. 不用“我也不知道，反正这样”逃避设计责任。
11. 不故意写错字、弄乱格式或加入废话来制造所谓的人味。
12. 注释最终要让后来的人更容易改代码、少踩坑，否则宁可不写。

真正自然的注释，不是靠几个口头禅堆出来的。它来自一个很简单的前提：写注释的人真的知道这里为什么这样写，然后愿意用最平常的话，把这件事告诉下一个人。
